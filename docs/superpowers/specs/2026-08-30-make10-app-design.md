# MAKE10 モバイルアプリ 設計仕様書

- 作成日: 2026-08-30
- 対象プラットフォーム: iOS / Android（単一コードベース）
- ステータス: 設計確定・実装計画待ち

## 1. 概要

4つの数字を四則演算で組み合わせて 10 を作るパズルゲーム。切符番号やナンバープレートで遊ばれてきた「メイクテン」をアプリ化する。

Flutter による単一コードベースで iOS と Android の両方を提供する。完全オフラインで動作し、アカウント登録・ネットワーク通信・課金・広告のいずれも v1 では持たない。

### 1.1 v1 のスコープ

含むもの:

- プラクティスモード（時間制限なし）
- タイムアタックモード（120秒）
- 難易度選択（やさしい / ふつう / むずかしい）
- ヒント（次の一手）
- 答えを見る
- 端末内の統計・ベストスコア保存

含まないもの（v1 では実装しない）:

- サウンド・ハプティクス
- オンラインランキング、アカウント、サーバー通信
- デイリーチャレンジ、ステージ制
- 広告、課金
- 多言語対応（UI は日本語のみ。ローカライズ機構は持たない）

## 2. ゲームルール

### 2.1 出題

- 0〜9 の数字を 4 つ提示する（重複あり）
- **必ず解が存在する組み合わせのみ**を出題する
- 提示順は抽選ごとにシャッフルする

**重複回避**: 難易度別のプールは 172〜192 問しかないため、素朴な乱数抽選では短時間で同じ問題が再出現する。**直近 50 問に出題した問題は抽選対象から除外する**。除外後の候補が空になることはない（最小プールでも 172 問あり、50 問を除いても 122 問残る）。

出題履歴は難易度別に保持し、アプリを再起動しても維持する（再起動のたびに同じ問題から始まるのを避けるため）。保存形式は §8.3 を参照。

### 2.2 演算ルール

- 使える演算子は `+` `-` `×` `÷` の 4 つ
- **途中経過は整数のみ**。割り切れない除算は実行できない（例: `7 ÷ 2` は不可）
- **負の数は許可**する（例: `3 - 8 = -5` は有効な一手）
- 0 での除算は実行できない
- 4 つの数字はすべて 1 回ずつ使う
- 数字の連結（`1` と `2` から `12` を作る等）は認めない

負数の許可は、解ける問題の数には影響しない（§5.2 の実測のとおり、負数を経由しないと解けない問題は 0 件）。それでも許可するのは、禁止するとプレイ中に「負になる合成」を毎回拒否することになり、操作を弾かれる体験が増えるため。**許可は解の存在ではなく操作の自由度のための選択**である。

### 2.3 勝利条件

3 回の合成を経て残った 1 枚の値が **ちょうど 10** であること。

### 2.4 操作モデル（カード合成型）

盤面には数字カードが並ぶ。初期状態は 4 枚。

1. カード A をタップ → 選択状態になる
2. 演算子をタップ → 画面に `A op ?` と表示される
3. カード B をタップ → `A op B` の結果が新しいカード 1 枚になり、A と B は盤面から消える

盤面は 4 枚 → 3 枚 → 2 枚 → 1 枚と縮む。

この順序（左オペランド → 演算子 → 右オペランド）を採用する理由は、`-` と `÷` の向きが操作から一意に決まり、かつ電卓と同じ入力感覚になるため。

キャンセル操作:

- 選択中のカードを再タップすると選択解除
- 演算子を選択中に別の演算子をタップすると演算子を差し替え

### 2.5 拒否される操作

| 操作 | 挙動 |
|---|---|
| 割り切れない除算 | 合成せず、対象カードを横方向に震わせるアニメーション + 「割り切れません」を短時間表示 |
| 0 での除算 | 同上（「0 では割れません」） |
| 最後の 1 枚が 10 以外 | 自動では戻さない。「10 になりませんでした」を表示し、Undo を促す |

拒否された場合、**カード A の選択と演算子の選択は維持する**（`A op ?` の状態に戻る）。ユーザーは B を選び直すだけで済み、A から選び直させられずに済む。

### 2.6 Undo / リセット

- **Undo**: 直前の合成 1 手を取り消す。何手でも遡れる
- **リセット**: 初期の 4 枚に戻す

合成型は一手あたりの重みが大きく、取り消せないとストレスが強い。両方とも v1 必須機能とする。

## 3. 補助機能

### 3.1 ヒント（次の一手）

現在の盤面（1〜4 枚）に対してソルバーを実行し、10 に到達可能な手を 1 つ提示する。該当する 2 枚のカードを強調表示し、使うべき演算子を示す。実際の合成はユーザーが行う。

盤面が進んだ後でも機能する点が、カード合成型と実行時ソルバーの組み合わせの利点である。

**ヒントは決定的である。** 同じ盤面で何度押しても同じ手を返す（探索順を固定し、最初に見つかった手を返す。§7.3）。押すたびに違う手が出ると、ユーザーは「どれが正解なのか」を判断できなくなる。

盤面に同じ値のカードが複数ある場合（例: `5, 5, 3`）でも、ソルバーは**カードの位置（インデックス）**で手を返すため、強調すべきカードは一意に定まる。

### 3.2 詰み検出

ヒントを押した時点で、現在の盤面から 10 に到達不能な場合は「この手順からは 10 を作れません。戻しましょう」と表示する。

詰みを常時監視して自動表示することはしない。ユーザーが試行錯誤している最中に割り込むのはお節介であり、また「詰んだことに自分で気づく」ことがパズルの一部であるため。**詰み検出はヒント押下時にのみ発火する。**

### 3.3 答えを見る

解答例を 1 つ、手順の形で表示する。

```
3 × 4 = 12
12 - 9 = 3
3 + 7 = 10
```

表示後は当該問題を「答えを見た」として記録し、クリア数には計上しない。

**答えを見た問題は続行できない。** 解答例を表示したら盤面の操作を止め、「次の問題へ」ボタンのみを出す。答えが分かった状態で合成を再開させても意味がないため。

### 3.4 スキップ

現在の問題を放棄して次の問題へ進む。ペナルティはない。

## 4. ゲームモード

### 4.1 プラクティス

- 時間制限なし
- ヒント・答えを見る・スキップすべて利用可能
- 1 問クリアするごとに次の問題を出題し、ユーザーが中断するまで続く
- クリア数・解答時間を統計に記録する

**ヒントを使ってクリアした問題もクリア数に計上する。** 最後まで手を進めたのはユーザー自身であるため。ヒントの使用回数は `hintUsed` に別途記録し、統計画面で「ヒント使用 12 回」のように併記する。

一方、**答えを見た問題とスキップした問題はクリア数に計上しない**（自力で解いていないため）。

### 4.2 タイムアタック

- 制限時間 **120 秒**
- スコアはその間の **クリア数**
- スキップ可能（ペナルティなし、即座に次の問題）
- **ヒントと答えを見るは無効**

ヒントを無効にする理由は、プラクティスで練習しタイムアタックで競う、という役割分担を明確にするため。ヒントが使えるとスコアの意味が失われる。

**この帰結として、タイムアタック中は詰み検出も働かない。** 詰み検出はヒント押下時にのみ発火する仕様（§3.2）であり、そのヒントが無効だからである。詰んだ盤面に気づかないまま時間を消費する可能性があるが、**これは意図した仕様**とする。詰みに気づくこと自体を競技の一部と位置づける。Undo・リセット・スキップはタイムアタック中も使えるため、行き止まりから抜ける手段は用意されている。

**時間切れの扱い**: 残り時間が 0 になった時点で即座に終了する。解答中だった問題はスコアに計上しない（クリアしていないため）。カウントダウンや猶予は設けない。

終了時にリザルト画面へ遷移し、スコアとベスト更新の有無を表示する。「もう一度」は**同じ難易度で**再スタートする。

### 4.3 難易度

プレイ開始前に「やさしい / ふつう / むずかしい」から選択する。両モード共通。統計とベストスコアは難易度別に記録する。

## 5. 難易度の定義

### 5.1 指標

難易度は **解の本数 `n`（正規化後にユニークな解の総数）のみ**で決める。少ないほど難しい。

当初は補助指標として「除算必須 (`div`)」と「負数必須 (`neg`)」も加える予定だったが、いずれも採用しなかった。

- `neg` は実測の結果 **該当する問題が 0 件**であり、指標として機能しない（§5.2）
- `div` は「除算が必要だと体感難易度が跳ねる」という推測にもとづくもので、裏づけがない。`n` は 1〜96 と十分な解像度があるため、まず `n` 単独で運用する

`div` の値自体は `puzzles.json` に記録しておく（101 問が該当）。実際に遊んで除算問題だけ難しいと分かった場合に、v2 で補正を導入できるようにするため。

### 5.2 実測データ

本仕様の作成にあたり、ソルバーの試作で全 715 通りを解いて以下を確認した。実装後は生成スクリプトがこの値を再現するはずであり、乖離した場合はソルバーの不具合を疑う。

| 項目 | 値 |
|---|---|
| 総組み合わせ（0〜9 から 4 つ、重複あり） | 715 |
| 解あり | 548 |
| 解なし | 167 |
| 解の本数の範囲 | 1 〜 96（中央値 16） |
| 除算必須の問題 | 101 |
| 負数必須の問題 | 0 |
| 負数を禁止した場合の解あり数 | 548（負数の許可は解の存在に影響しない） |

### 5.3 分類方法

解の本数 `n` の分位点で 3 分割する。他の指標による補正は行わない。

上記の実測にもとづく分割は次のとおり。

| 難易度 | 条件 | 問題数 |
|---|---|---|
| むずかしい | `n` ≤ 9 | 184 |
| ふつう | 10 ≤ `n` ≤ 26 | 192 |
| やさしい | `n` ≥ 27 | 172 |

**閾値 9 / 26 はコードにハードコードしない。** 生成スクリプトが分位点から算出して `puzzles.json` の `thresholds` に書き出す。ルールを変更した際に閾値が自動追従するようにするため。

### 6.3 問題データの生成方針

ソルバーの実装は **1 本のみ**とし、ビルド時のテーブル生成にも実行時のヒントにも同じコードを使う。

- `tool/generate_puzzles.dart` が `lib/domain/solver.dart` を 715 通りに対して実行し、`assets/puzzles.json` を生成する
- 生成物はリポジトリにコミットする
- 「再生成した結果がコミット済みのものと一致する」ことをテストで担保し、ソルバーとテーブルの乖離を防ぐ

事前計算が必要なのは「難易度でプールを分割する」という一点のみ。**解答例はテーブルに含めない**（ソルバーがアプリに載っているため実行時に生成できる）。

### 6.4 ドメインモデル

主要な型を先に定めておく。フィールド名は実装時に調整してよいが、**責務の切り方は変えない**こと。

```dart
enum Op { add, sub, mul, div }

/// 盤面上の 1 枚。値が同じカードを区別するため id を持つ。
/// id は 1 問のなかで一意であればよい（連番）。
class CardItem {
  final int id;
  final int value;
}

/// ソルバーが返す手。カードを「盤面リスト内の位置」で指す。
/// 値ではなく位置で指すことで、同じ値のカードが複数あっても曖昧にならない。
class SolverMove {
  final int leftIndex;
  final int rightIndex;
  final Op op;
  final int result;
}

/// 盤面に適用済みの手。カードを id で指す。
class Move {
  final int leftId;
  final int rightId;
  final Op op;
  final CardItem produced;
}

/// 解の 1 手。表示用なので位置ではなく値で持つ。
class SolutionStep {
  final int left;
  final int right;
  final Op op;
  final int result;
}

/// 1 つの解。3 手の列と、重複排除に使う正規形キー。
class Solution {
  final List<SolutionStep> steps;
  final String canonical;
}

/// 盤面。cards は 1〜4 枚。history は適用順の手。
/// apply は失敗しうる（割り切れない除算・0 除算）ため戻り値で成否を表す。
class Board {
  final List<CardItem> cards;
  final List<Move> history;

  Board? apply(int leftId, int rightId, Op op);  // 失敗時 null
  Board undo();      // history が空なら自分自身を返す
  Board reset();     // 初期の 4 枚に戻す
  bool get isCleared;   // cards が 1 枚かつ値が 10
  bool get isFinished;  // cards が 1 枚（値は問わない）
}
```

`Solution` が `SolverMove` ではなく `SolutionStep` を持つのは、盤面が縮むにつれてインデックスの意味が変わるため。3 手を通した表示（`3 × 4 = 12` → …）には値のほうが直接使える。位置で指す必要があるのは「いま強調するカード」を決めるヒントだけである。

`SolverMove`（位置で指す）と `Move`（id で指す）を分けているのは、ソルバーが盤面の履歴やカード id を知る必要がないため。ソルバーは `List<int>` だけを扱う純粋な関数であり、id との対応づけはゲーム層の責務とする。

## 7. ソルバー

### 7.1 探索

与えられた値のリストから 2 枚を選んで 1 枚に置き換える操作を繰り返す、素朴な全列挙。4 枚 → 3 枚 → 2 枚 → 1 枚と縮む。

**入力リストの並びは変更しない。** `hint` が返す `leftIndex` / `rightIndex` は呼び出し元が渡したリストの位置を指す。ソルバーが内部でソートすると、盤面 `5, 3, 5` に対して返したインデックスが呼び出し元の並びとずれ、UI が誤ったカードを強調してしまう。生成スクリプトは昇順の組み合わせを渡すが、それは呼び出し側の都合であってソルバーの前提ではない。

**メモ化はしない。** 多重集合をキーに結果をキャッシュすれば経路数は減らせるが、`solve` は到達値ではなく**式木**を列挙する必要があり、多重集合でキャッシュすると異なる部分式が潰れて解の本数を誤る。経路数は次のとおり十分小さく、メモ化する理由がない。

経路数の上限は `36 × 18 × 6 = 3,888`（4 枚時に 6 ペア × 6 演算、3 枚時に 3 ペア × 6 演算、2 枚時に 1 ペア × 6 演算）。715 通りすべてを解いても約 280 万経路であり、生成も実行時ヒントも実用上ゼロコスト。試作では 715 通りの全解列挙が数秒で完了した。

「6 演算」とは、選んだ 2 枚 `a` `b` に対する `a+b` `a-b` `b-a` `a×b` `a÷b` `b÷a` の 6 通りを指す。

割り切れない除算と 0 除算は探索時点で枝刈りする。

### 7.2 解の正規化

解の本数を数える際は正規形で重複排除する。`3 + 7` と `7 + 3` を別解として数えると可換演算の分だけ本数が膨らみ、難易度指標として機能しないため。

式木を構築し、可換演算（`+`, `×`）については子ノードをソートしたうえでシリアライズし、その文字列をキーとして集合に入れる。

### 7.3 API

| 関数 | シグネチャ | 用途 |
|---|---|---|
| `solve` | `List<Solution> solve(List<int> values)` | 10 に到達する全解を正規形で返す。難易度計算と「答えを見る」に使用 |
| `hint` | `SolverMove? hint(List<int> values)` | 10 に到達可能な次の一手を 1 つ返す。到達不能なら null |
| `isDeadEnd` | `bool isDeadEnd(List<int> values)` | 10 に到達できない盤面かを返す。詰み判定 |

`isDeadEnd` は **`hint` が null であることと同値ではない**。カードが 1 枚でその値が 10 の盤面（クリア済み）では `hint` は null を返すが、詰みではない。`isDeadEnd` は「10 に到達可能か」を直接判定する内部関数で実装し、`hint` の戻り値からは導出しない。

**探索順を固定し、`hint` を決定的にする。** ペアは `leftIndex` 昇順・`rightIndex` 昇順、演算子は `add` → `sub` → `mul` → `div` の順に試し、10 に到達可能と分かった最初の手を返す。同じ盤面には常に同じヒントが返る。

`hint` が返すのは `SolverMove`（位置で指す）であり、盤面に同じ値のカードが複数あっても強調表示すべきカードは一意に定まる。

## 8. データ定義

### 8.1 puzzles.json

```json
{
  "version": 1,
  "rule": { "target": 10, "division": "exact", "negatives": true },
  "thresholds": { "hard": 9, "normal": 26 },
  "puzzles": [
    { "d": [1, 5, 5, 5], "n": 1, "div": true, "lv": "hard" },
    { "d": [0, 1, 2, 8], "n": 96, "div": false, "lv": "easy" }
  ]
}
```

| フィールド | 意味 |
|---|---|
| `version` | スキーマバージョン。読み込み時に検証する |
| `rule` | 生成時に用いたルール。アプリ側のルールと一致するか起動時に検証する |
| `thresholds` | 生成時に算出した分位点。`hard` / `normal` の境界となる解の本数 |
| `d` | 4 つの数字（昇順） |
| `n` | 正規化後の解の本数 |
| `div` | 除算を使わないと解けないか。**v1 では未使用**（将来の難易度調整のために記録するのみ。§5.1） |
| `lv` | `easy` / `normal` / `hard`。`n` と `thresholds` から決まる |

解ありの 548 問のみを収録する（解なしの 167 通りは出題しないため含めない）。想定サイズは 548 行、数十 KB。

### 8.2 統計データ

`shared_preferences` に単一の JSON 文字列として保存する。

```json
{
  "version": 1,
  "practice": {
    "easy":   { "solved": 0, "totalTimeMs": 0, "hintUsed": 0, "answerShown": 0, "skipped": 0 },
    "normal": { "solved": 0, "totalTimeMs": 0, "hintUsed": 0, "answerShown": 0, "skipped": 0 },
    "hard":   { "solved": 0, "totalTimeMs": 0, "hintUsed": 0, "answerShown": 0, "skipped": 0 }
  },
  "timeAttack": {
    "easy":   { "bestScore": 0, "playCount": 0 },
    "normal": { "bestScore": 0, "playCount": 0 },
    "hard":   { "bestScore": 0, "playCount": 0 }
  }
}
```

平均解答時間は `totalTimeMs / solved` で導出する。ヒントを使ってクリアした問題は `solved` に計上する（§4.1）。答えを見た問題とスキップした問題は計上しない。

### 8.3 出題履歴

重複回避（§2.1）のため、難易度別に直近 50 問の出題履歴を保持する。統計とは責務が異なるため、`shared_preferences` の**別キー**に保存する。

```json
{
  "version": 1,
  "easy":   [[0,1,2,8], [0,0,1,9]],
  "normal": [],
  "hard":   [[1,5,5,5]]
}
```

各配列は新しいものが先頭。長さが 50 を超えたら末尾から捨てる。読み込みに失敗した場合は空履歴として続行する（重複が一時的に増えるだけで、プレイは妨げられない）。

**履歴はモード間で共有する。** キーは難易度のみで、プラクティスとタイムアタックを区別しない。プラクティスで解いた直後の問題がタイムアタックで出るのを避けるため。

## 9. 画面構成

| 画面 | 内容 |
|---|---|
| ホーム | タイトル、モード選択（プラクティス / タイムアタック）、統計へのリンク |
| 難易度選択 | やさしい / ふつう / むずかしい。選択後にゲーム画面へ |
| ゲーム | 盤面カード、演算子バー、アクションバー、（タイムアタック時）残り時間とスコア |
| リザルト | タイムアタック終了時のみ。スコア、ベスト更新表示、もう一度 / ホーム |
| 統計 | 難易度別のクリア数・平均解答時間・ヒント使用回数・答えを見た回数・スキップ回数・タイムアタックのベストスコア |

### 9.1 ゲーム画面のレイアウト

上段から順に:

1. ステータス行 — プラクティスなら問題番号、タイムアタックなら残り時間とスコア
2. 盤面 — カード 1〜4 枚。合成に伴って枚数が減る。選択中のカードと `A op ?` の表示
3. 演算子バー — `+` `-` `×` `÷`
4. アクションバー — Undo / リセット / ヒント / 答え / スキップ（タイムアタック時はヒントと答えを非活性化）

### 9.2 画面サイズ対応

盤面・演算子バー・アクションバーの 3 段構成を縦方向の `Column` で組み、カードのサイズだけを利用可能な高さに応じて変える。小型端末（iPhone SE 相当）でスクロールなしに全要素が収まることを最低条件とする。

タブレットではカードを拡大せず、**盤面の最大幅を制限して中央寄せ**する。カードが視野いっぱいに散らばると 4 枚の関係が把握しづらくなるため。

横向き（landscape）は v1 では対応せず、縦向き固定とする。

## 10. エラー処理

| 事象 | 対応 |
|---|---|
| 割り切れない除算・0 除算 | 合成を実行せず、カードの震えアニメーションと短時間のメッセージ |
| 最後の 1 枚が 10 以外 | メッセージ表示のみ。盤面は変更せず Undo を促す |
| `puzzles.json` の読み込み失敗 | 起動時にエラー画面を表示。アセット欠落を検出するための保険 |
| `puzzles.json` の `version` 不一致 | 同上 |
| `puzzles.json` の `rule` がアプリのルールと不一致 | 同上。ルール変更時のテーブル再生成漏れを検出する |
| 統計データの読み込み失敗・破損 | 初期値にフォールバックして続行。ゲームプレイを妨げない |
| 出題履歴の読み込み失敗・破損 | 空履歴として続行。一時的に重複が増えるだけで、プレイは妨げられない |

## 11. テスト戦略

### 11.1 ドメイン層（単体テスト）

ソルバーのテストには、試作で検証済みの以下の固定値を使う。実装したソルバーがこの表を再現できなければ不具合である。

| 入力 | 期待値 |
|---|---|
| `1,5,5,5` | 解の本数 1、唯一解は `((5 / 5) + 1) × 5`、`div` = true |
| `1,1,1,4` | 解の本数 1、唯一解は `(1 + 1) × (1 + 4)` |
| `0,2,2,9` | 解の本数 14、`div` = true（除算なしでは解けない） |
| `3,4,7,9` | 解の本数 18 |
| `0,1,2,8` | 解の本数 96（最大） |
| `1,1,1,1` | 解なし |
| `1,1,9,9` | 解なし（整数のみルールでは到達不能） |

加えて:

- **正規化**: `3+7` と `7+3` が同一解として数えられること
- **演算規則**: 割り切れない除算と 0 除算が失敗を返すこと、負数が許容されること
- **盤面**: 合成、Undo（複数手）、リセット、クリア判定
- **ヒントの決定性**: 同じ盤面に対して `hint` を複数回呼ぶと常に同じ `SolverMove` が返ること
- **入力順を保つこと**: 未ソートの盤面（例: `5, 3, 5`）を渡したとき、`hint` が返す `leftIndex` / `rightIndex` が**渡した並びの位置**を指すこと。ソルバーが内部でソートしていないことをこのテストで担保する
- **同値カードの区別**: 盤面 `5, 5, 3` に対する `hint` の `leftIndex` / `rightIndex` で、強調すべきカードが一意に定まること
- **詰み判定**: 解ける問題から意図的に詰み盤面へ進め、`isDeadEnd` が真になること

### 11.2 生成物の整合性

- `puzzles.json` を再生成した結果がコミット済みのものと完全一致すること
- 収録件数が 548 件であること
- 全問について、ソルバーが実際に解を 1 つ以上返すこと
- 各問の `n` `div` がソルバー再実行の結果と一致すること
- 難易度の内訳が むずかしい 184 / ふつう 192 / やさしい 172 であること

### 11.3 ゲーム進行

- タイムアタックの時間切れ、スコア加算、ベストスコア更新
- ヒントを使ってクリアした問題がクリア数に計上され、かつ `hintUsed` も増えること
- 答えを見た問題・スキップした問題がクリア数に計上されないこと
- 統計の永続化と読み戻し
- **重複回避**: 直近 50 問に出た問題が再抽選されないこと。履歴が 50 件を超えたら古いものから捨てられること
- **履歴の永続化**: アプリ再起動後も出題履歴が維持されること

### 11.4 Widget テスト

- ゲーム画面で 4 枚から 3 手でクリアするフロー
- **プラクティスで**詰み盤面のヒントを押すと「戻しましょう」が表示されるフロー
- 答えを見た後は盤面を操作できず、「次の問題へ」のみが出ること
- タイムアタック中にヒント・答えボタンが非活性であること
- 割り切れない除算を試みたとき、カード A と演算子の選択が維持されること

## 12. 決定事項の記録

議論の過程で採用しなかった案と、その理由。

| 論点 | 採用案 | 不採用案と理由 |
|---|---|---|
| 問題の用意 | ビルド時にテーブル生成 | 実行時に乱数抽選 + 判定。難易度別に出題するとリジェクションサンプリングになり、出現率の低い難易度で引き直しが多発する |
| ソルバーの数 | 1 実装をビルド時と実行時で共用 | テーブルとソルバーを別々に持つ二重管理 |
| 解答例の保存 | テーブルに含めない | ソルバーが実行時に載っているため冗長 |
| 詰み検出 | ヒント押下時のみ | 常時監視して自動表示するのは試行錯誤への割り込みになる |
| 入力順序 | 左オペランド → 演算子 → 右オペランド | ドラッグ&ドロップ（実装が重く誤操作が増える）、式を文字列で組み立てる方式（入力ミスが増える） |
| 途中経過の数値 | 整数のみ・負数可 | 分数許容（難問の幅は広がるがルールが複雑） |
| 難易度指標に `neg` を含めるか | 含めない | 負数必須の問題が実測で 0 件だったため、指標として機能しない |
| 難易度指標に `div` を含めるか | 含めない（データには残す） | 「除算必須だと難しい」は裏づけのない推測。`n` の解像度で足りる。必要なら v2 で導入する |
| タイムアタック中の詰み | 何もしない（詰みに気づくことも競技の一部とする） | 詰み検出のみ有効化する案、詰み時に自動リセットする案（いずれも「助けが入る／勝手に盤面が変わる」ことになり、競技性を損なう） |
| ヒント使用時のクリア数 | 計上する | 計上しない案もあるが、最後まで手を進めたのはユーザー自身。使用回数は別カウンタで可視化する |
| 出題の重複回避 | 直近 50 問を除外 | プールを 1 周させる（実装が重い）、直近 20 問（プールの 1 割強では体感的に足りない） |
| ソルバーの手の指し方 | 位置（インデックス） | 値で指すと同値カードが 2 枚あるときに曖昧になる |
