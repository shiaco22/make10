# ボーナスゲーム 1 日 5 回まで 設計仕様書

- 作成日: 2026-09-06
- ステータス: 設計確定・実装計画待ち
- **この文書は [2026-09-03-make10-bonus-game-design.md](2026-09-03-make10-bonus-game-design.md) の §4（解禁と 1 日 1 回の権利）を全面的に、§5（データ定義）・§7.1（ホーム画面）・§7.2（タイムアタックのリザルト）を部分的に上書きする。**
- ボーナスゲーム本体のルール（入れ替え 10 回の上限、ゲームオーバー、スコア式、エフェクト）は [2026-09-05-bonus-gameover-and-effects-design.md](2026-09-05-bonus-gameover-and-effects-design.md) のまま。本書は**遊べる回数だけ**を変える。

## 1. 変更の要旨

ボーナスゲームを **1 日 1 回から 1 日 5 回まで**に増やす。

回数は自動で配られない。**タイムアタックで 5 問クリアするたびに 1 回分たまり、1 日あたり 5 回で頭打ちになる。** ボーナスを 5 回遊ぶにはタイムアタックを 5 回勝つ必要がある。

この形にした理由は、ボーナスが「タイムアタックを遊ぶ理由」であり続けるため。1 回クリアすればその日 5 回開く形にすると、一度通ったあとはボーナスだけを繰り返す遊び方になり、タイムアタックの位置づけが薄れる。

### 1.1 スコープ

含むもの:

- 1 日あたりの回数（5）と、獲得の単位（タイムアタック 5 問クリア 1 回につき 1）
- 既存の保存データからの移行
- ホーム画面とタイムアタックのリザルトの表示

含まないもの:

- ボーナスゲーム本体のルール変更
- 結果画面の「もう一度」（ホームへ戻って押し直すのが 2 タップで済み、状態が 1 つ増える割に得るものが小さい）
- 回数を増やす手段（広告視聴・課金・アイテム）
- 回数の繰り越し

## 2. 権利の持ち方

### 2.1 なぜ作り直すのか

現在の `BonusTicket` は「解禁した日」と「遊んだ日」の 2 つの日付だけを持つ。**日付では数が数えられない**ので、回数制にするには表現そのものを変える必要がある。

日付 1 つとカウンタ 2 つにする。

```dart
/// 1 日に遊べる最大回数。
const int kBonusPlaysPerDay = 5;

class BonusTicket {
  String? day;   // このカウンタが属するローカル日付
  int earned;    // その日に獲得した回数（0..kBonusPlaysPerDay）
  int played;    // その日に開始した回数
}
```

日付を `yyyy-MM-dd` のローカル日付文字列で持つ点は変えない。整数の秒やミリ秒では、サマータイムや端末の時刻変更で日付境界の判定が壊れる。

### 2.2 操作

| 操作 | 意味 |
|---|---|
| `earn(today)` | タイムアタックで [kBonusUnlockClears] 問以上クリアしたときに呼ぶ。`day` が今日でなければ先に全部リセットしてから `earned` を 1 増やす（[kBonusPlaysPerDay] で頭打ち）。**実際に `earned` が増えたら true**（上限に達していれば false）|
| `isAvailable(today)` | `day == today && played < earned` |
| `consume(today)` | ボーナスゲームを**開始した**ときに呼ぶ。`played` を 1 増やす |
| `playsLeft(today)` | `day == today ? earned - played : 0` |

- 日付が変わればカウンタごとリセットされる。**繰り越しはない**
- `earned` が [kBonusPlaysPerDay] に達したあとのタイムアタック勝利は何も増やさず、`earn` は false を返す
- **`earn` の返り値は「増えたか」であって「遊べるようになったか」ではない。** 既に遊べる状態で 2 個目を獲得した場合も true になる。リザルトの告知（§5）はこの返り値で出すので、獲得のたびに出る必要がある
- `consume` は `day` が今日でなければ何もしない（起こらないはずだが、`isAvailable` を通らずに呼ばれた場合にカウンタを壊さない）

### 2.3 消費は開始時のまま

完了時ではなく開始時に消費する理由は変わらない（前提仕様 §4.3）。完了時にすると強制終了で無限にリトライできる。中断で回数を失う実害は、途中の盤面を永続化して再開できるようにすることで消してある。

**中断中の 1 回は消費済みとして数える。** 途中の盤面を持ったまま別の回を始めることはできない（ホーム画面は中断の再開を最優先で出す。§4）。

## 3. 既存の保存データからの移行

`make10.bonus` には `unlockedOn` / `playedOn` を持つ古い形式が既に存在する（web 版は公開済みで、実際に遊んだ人のデータがある）。**捨てるとその日の権利が消える**ので、読み込み時に変換する。

| 保存されている値 | 変換後 |
|---|---|
| `unlockedOn` も `playedOn` も無い | `day = null, earned = 0, played = 0` |
| `unlockedOn` のみ | `day = unlockedOn, earned = 1, played = 0` |
| `playedOn` のみ | `day = playedOn, earned = 1, played = 1` |
| 両方あり、同じ日 | `day = その日, earned = 1, played = 1` |
| 両方あり、`unlockedOn` の方が新しい | `day = unlockedOn, earned = 1, played = 0` |
| 両方あり、`playedOn` の方が新しい | `day = playedOn, earned = 1, played = 1` |

`playedOn` があるのに `unlockedOn` が無い組み合わせは、遊んだのなら獲得もしていたはずなので `earned = 1` とする。

新しい形式で保存されたあとは、古いキーは書かない。**`day` が存在すれば新形式として読み、`unlockedOn` / `playedOn` は無視する**（同じ端末で新旧のビルドを行き来した場合に、古い方の値で上書きしない）。

## 4. ホーム画面

入口の状態は 4 つ。**うち 2 つは同じ文言に畳む。**

| 状態 | 表示 | 押せるか |
|---|---|---|
| 中断あり | ボーナスゲーム（続きから） | 押せる |
| 残り 1 以上 | ★ ボーナスゲーム（あと N 回） | 押せる |
| 残り 0・今日の上限に未到達 | ボーナスゲーム（タイムアタックで5問クリア） | 押せない |
| 今日 5 回使い切った | ボーナスゲーム（また明日） ベスト N | 押せない |

3 行目を未獲得のときと同じ文言にするのは、**プレイヤーがやるべきことが同じ**だから。「まだ 1 回も獲得していない」と「獲得した分を使い切ったが今日の上限には届いていない」は、どちらも次の行動が「タイムアタックを勝つ」であり、区別しても情報が増えない。

中断の再開を最優先で出すのは今と同じ。中断中の 1 回は消費済みなので、再開せずに別の回を始められると回数が合わなくなる。

## 5. タイムアタックのリザルト

5 問以上クリアしたときの告知を、回数が分かる形に変える。

| 状況 | 表示 |
|---|---|
| 獲得した（残り N 回） | ボーナスゲーム +1回（あと N 回） |
| 既に今日の上限（5 回獲得済み） | 出さない |
| 5 問未満 | 出さない |

上限に達しているときに何も出さないのは、「+1回」と出しておいて実際には増えていない、という嘘を避けるため。

## 6. データ定義

`make10.bonus` の JSON を変える。

```json
{
  "version": 2,
  "bestScore": 859,
  "day": "2026-09-06",
  "earned": 3,
  "played": 2,
  "inProgress": { "grid": [1, 2, "...25 要素..."], "score": 340, "repairsUsed": 4 }
}
```

- `version` を 2 に上げる。読み込み側は 1 と 2 の両方を受ける（§3）
- `day` は未設定なら `null`。`earned` / `played` は 0 以上 [kBonusPlaysPerDay] 以下に丸める
- `earned < played` になる保存データは壊れているので、`played = earned` に丸める（回数が増える側ではなく減る側に倒す）
- 読み込みが失敗したときは初期値で続行する。既存 `StatsRepository.load` と同じ方針

## 7. エラー処理

| 事象 | 挙動 |
|---|---|
| `earned` / `played` が範囲外・型違い | 0 として読む |
| `earned < played` | `played` を `earned` に丸める |
| `day` が日付として不正な文字列 | そのまま保持する。今日と一致しないので `playsLeft` は 0 になり、次の `earn` でリセットされる |
| `version` が 3 以上（将来のビルドで保存されたデータ） | 既知のキーだけ読む。読めないキーは既定値 |

## 8. テスト戦略

### 8.1 カウンタ（`bonus_ticket.dart`）

- 初期状態では遊べない
- `earn` 1 回で 1 回遊べる
- `earn` を 5 回で 5 回遊べる
- `earn` を 6 回しても 5 回のまま。6 回目の `earn` は false を返す
- `consume` するたびに残りが減る
- 獲得した数より多く遊べない
- **`earn` → `consume` → `earn` で、また遊べるようになる**（1 日 1 回の頃はここが false だった。回数制で最も変わる点）
- 日付が変わるとカウンタがリセットされ、繰り越さない
- 前日に獲得して遊ばなかった分は翌日に消える

### 8.2 移行（`bonus_repository.dart`）

§3 の表の 6 通りすべてを、実際の旧形式 JSON から読んで検査する。**特に「`unlockedOn` のみ」（＝今日獲得してまだ遊んでいない）で、移行後に 1 回遊べること。**

新旧のキーが両方ある JSON で新しい方が優先されることも検査する。

### 8.3 ホーム画面（Widget テスト）

- 4 状態それぞれの文言と押せるかどうか
- 残り回数が表示に出る（あと 3 回 → あと 2 回）
- 中断があるときは、残り回数があっても「続きから」が優先される

### 8.4 タイムアタックの配線（Widget テスト）

- 5 問クリアで残りが 1 増える
- 4 問では増えない
- 5 回獲得済みの状態で 6 回目を勝っても増えず、告知も出ない
- 告知に残り回数が出る

### 8.5 既存の回帰

- ボーナスゲーム本体（入れ替え 10 回、ゲームオーバー、エフェクト）は無変更で通る
- 中断・再開で `repairsUsed` が戻らない（前回塞いだ抜け道）
